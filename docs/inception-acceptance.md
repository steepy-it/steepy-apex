# Inception acceptance protocol

How to prove, in a real harness, that the `inception` skill takes a new application from its
starting materials to a verified bootstrap, then to a hub built by `init`. The protocol is
reproducible. Its results are observations of real runs. Read the [inception guide](inception.md)
first.

## What this protocol proves

- The hermetic suite `tests/inception-integration.test.mjs` runs the real helpers and public CLIs
  on synthetic data; it is not native evidence. It proves the deterministic part: formats,
  digests, the pre-hub linter, resume, and a hub that stands on its versioned files. It runs no
  harness, model, install, build, start, or deploy.
- This protocol observes what only a native run shows: the harness discovers and invokes the
  skill, the model follows it, a real bootstrap works, and `init` turns it into a hub.
- A native result covers the observed run only. The hermetic suite never produces a native
  result, and a native result never replaces the hermetic suite.

## Approver for this release

Decision (2026-09-24): native runs for this release use a model approver. The model that drives
the harness answers the approval questions, not a human. The human approval gate is exercised
with a model approver, so a PASS here never counts as observed human approval. Every result
names its approver.

## Before each run

- Record the plugin revision: the full commit SHA of the checkout under test.
- Load that checkout the way [Installation](installation.md) describes for the harness. For
  Claude Code, `claude --plugin-dir <plugin-checkout>` loads it without installing.
- Record the harness, its version, and its capabilities: subagents, shell, network, browser,
  question UI.
- Create the test project in an exact temporary directory outside every repository checkout.
  Nothing is written in the plugin checkout.
- Verify sources at run time. Every foundational choice names its official source, an explicit
  version, and the verification date. A remembered version is not a source.
- Use no paid service, publication, or real deploy unless the approved test project includes it.
  Deploy stays excluded by default. An uncertain deploy is simulated only in the hermetic suite
  and is never reported as a real deploy.
- Sign in only through the harness's own login. Never put a credential in the project, a prompt,
  or the evidence.

## Scenarios

Run each scenario through the public `inception` skill in a real harness. A hand-written command
sequence that imitates the skill is not a proof. The three scenarios may use different harnesses.
At least one scenario interrupts and resumes the run.

### Scenario A — empty repository

**Inputs:** an empty Git repository and a one-paragraph product idea as the first message. Keep
the exact text.

**Ecosystem:** JavaScript or TypeScript. The concrete stack is chosen and verified during the run.

**Observe:**
- the decisions the skill asks for, one at a time, and one approval of the whole project before
  bootstrap;
- a bootstrap with persistence: the representative path writes and reads a real data store;
- install, build, test, and start, each from a clean state, with their outputs;
- the whole representative path, end to end;
- `init` through its inception entry, then `validate-hub` green on the repository;
- a copy of only the versioned files (`git ls-files --cached --others --exclude-standard`) that
  passes `validate-hub` and holds nothing from `.apex/inception/` or `.apex/work/`.

**Judge:** PASS when every observation holds and the verification record keeps configured,
executed, succeeded, not-executed, and failed distinct. FAIL when a run contradicts one.

### Scenario B — starter plus design system or prototype

**Inputs:** a starter generated by its official tool, plus a small design system or UI prototype
(tokens, a few components, screens with mock data), committed before the run. List the flows the
prototype shows.

**Ecosystem:** may reuse scenario A's ecosystem.

**Observe:**
- the reconnaissance record separates real elements from mocks;
- the planned assets are reused, and the starter's initial behavior still works;
- one integrated representative path crosses the agreed boundaries with real data;
- every other prototype flow is kept in `project-context.md` under "Future flows" as context:
  no component claim, no spec, no started backlog.

**Judge:** as A. FAIL also when a mock is presented as a real component, or a future flow is
built or planned.

### Scenario C — asynchronous boundary or compatibility constraint

**Inputs:** a product idea with an asynchronous boundary (a queue, a worker, a webhook) or a hard
compatibility constraint (a pinned runtime or library version).

**Ecosystem:** Python or another ecosystem that is not JavaScript, chosen during the run.

**Observe:**
- official research for the boundary or constraint, plus an experiment when the documentation
  leaves the behavior open;
- the critical integration executed for real, with its output;
- an interruption after at least one concluded effect, then a resume from the exact paths of the
  resume note: the concluded effect is not repeated, and an effect with an uncertain outcome is
  reconciled by observing it;
- `init` and the versioned-files copy, as in A.

**Judge:** as A. FAIL also when a concluded effect repeats or the resume lists the run directory.

## Evidence to keep

For each run keep, outside the repository:

- the inputs: the exact first message and the starting materials;
- the harness, its version and capabilities, and the plugin revision;
- the sources consulted, with versions and dates;
- the approved project, the digests the approval binds, and the approver;
- every command with its result;
- the deploy state: excluded with its reason, or included with its evidence;
- the decisions promoted to the hub and the decisions excluded;
- the deferred flows kept as context;
- the result of the versioned-files copy gate.

Only the redacted summary goes into the tables below.

## Redaction

- Replace every credential, token, cookie, account ID, and personal email with `<redacted>`.
- Replace absolute local paths with `<home>`, `<tmp>`, or `<project>`.
- Never link to local artifacts: `.apex/inception/`, `.apex/work/`, temporary directories, or
  harness session stores.
- Quote command output only as far as the result needs.

## Judging and open proofs

- A result is one of `PENDING`, `PASS`, `FAIL`, `NOT RUN` (the harness lacks the capability), or
  `BLOCKED` (the run started and could not finish).
- A result other than `PENDING` records its observation date, the harness and its version, and
  the plugin revision.
- A blocked proof stays open. Record the reason and the work completed. It never becomes a PASS,
  and a review cannot call the bootstrap criteria met while it is open.
- `NOT RUN` means a missing capability, not a failure. Never invent a descriptor, runner, or
  adapter to fill it.
